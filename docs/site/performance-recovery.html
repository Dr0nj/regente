Performance and recovery operations

The performance changes address repeated definition loading, retry amplification in audit receipts, and full scheduler scans. They do not establish a production capacity rating. See the roadmap for qualification status and the capacity laboratory for workload limits.

Compatibility and rollout

This runtime requires schema 34 (it upgrades a schema 33 database in place by adding two partial indexes), protocol 2, and matching server/agent artifacts. Stop admission, drain or inventory active and uncertain executions, and back up the database, workspace, signing key, collector journal and agent journals before migration. Schema 33 adds audit reservations and transactional scheduler change notifications. It inventories seven audit slots for each nonterminal attempt, including uncertain attempts. An inherited backlog can exceed the configured limit: new admission then fails closed while reserved transitions remain available. Do not delete reservations or ledger entries to reopen admission.

Upgrade the independent collector before enabling -audit-batch-size 128. The default remains one record for compatibility with existing collectors. Upgrade the server with -scheduler-incremental=false first; enable -scheduler-incremental only after the comparison workload passes. Both switches are startup flags. Disabling incremental scheduling restores full evaluation on schema 33; it does not downgrade the database. Rollback to a schema-32 binary requires the complete matching pre-upgrade backup and reconciliation of subsequent external effects, not just replacing the executable.

Native systemd rollout

Follow the backup and restore procedure and upgrade contract before changing the installed service. Preserve the actual unit, environment file, binary versions and flags with the backup. Verify the restore in an isolated cell; an online database snapshot alone does not capture every journal or external effect.

The supplied regente-server.service starts the binary without arguments. These two performance switches are CLI flags, not environment variables. For that stock unit, a reviewed drop-in at /etc/systemd/system/regente-server.service.d/performance.conf can select the initial mode:

[Service]
ExecStart=
ExecStart=/usr/local/bin/regente-server -audit-batch-size=1 -scheduler-incremental=false

For a customized unit, preserve all existing arguments in the replacement ExecStart. The environment file remains in effect. Inspect the effective unit with systemctl cat regente-server, then apply the drop-in with systemctl daemon-reload and systemctl restart regente-server during the planned window. A restart changes process counters; start a new measurement interval.

Pause admission and investigate if evidence has a ledger gap, conflicting receipt, duplicate external effect, growing backlog without recovery or stalled execution. Production diagnosis of 2026-11-13

The first live profile of a production host (2 vCPU, SQLite, 28,800 jobs per daily, ten days of accumulated history) showed that the laboratory had missed costs that grow with history and with workspace size rather than with the load of the moment. The scheduler was not dispatching: the daily sat with 28,802 orders waiting, and the web UI never finished loading.

SQLite planner constraint. SQLite uses a partial index only when the query repeats the index predicate textually; it does not infer that state='running' implies state NOT IN ('succeeded','failed','cancelled'). Queries against these indexes must use db.ActiveAttemptPredicate and db.RetryWaitPredicate. TestTickQueriesNeverScanHistory fails if any per-tick query plans a table scan.

Upgrade. Schema 34 is applied at startup and only creates the two indexes. Building the instances index reads that table once. On the diagnosed host (231,000 instances in a 4 GB SQLite file, CPU throttled) the equivalent scan took 111 s, close to the default -migration-timeout of two minutes. On a database of that size or larger, apply the migration as its own step with a measured budget before starting the service, for example regente-server -migrate-only -migration-timeout=15m under the service account and environment. A binary older than this release refuses a schema 34 database, so keep the pre-upgrade backup until the new version is accepted.

Still open. The host showed 89 to 95% CPU steal during the diagnosis; whether that is provider throttling triggered by the sustained load above or contention from neighbours was not established. One million orders per day remains unqualified: the web UI still receives the whole daily, the audit trail shares the operational database, and SQLite remains a single-writer store. PostgreSQL is the supported backend for larger installations.

Definitions

The live workspace owns one immutable normalized snapshot. API readers receive isolated copies; WebSocket handshakes hash the authorized view without rebuilding or copying the graph. Force Order looks up one definition through the snapshot's ID index before checking folder write permission; it does not copy the entire workspace for authorization. Full-list copies reuse type layouts and preserve nested value types and isolation. Concurrent cold readers share a build. A cancelled HTTP reader does not cancel that shared work. Known file/Git mutations invalidate before and after changing the workspace and serialize against publication. A Git sync with unchanged HEAD and tracked files retains the hot snapshot; untracked files remain preserved. External changes are checked by content every 15 seconds, including same-size and same-mtime edits. The build compares the content it actually parsed with the surrounding digests; an unstable build is rejected.

Invalid definitions make the snapshot unavailable. /readyz reports this, and a WebSocket connection receives 503 with Retry-After before upgrade. Correct the workspace and wait for reconciliation. External tools publishing multiple files must use coordinated or atomic publication; independent filesystem writes are not a multi-file transaction. Old snapshots are retained only while existing readers use them.

Audit pressure and receipts

Admission reserves seven named slots for dispatch, acceptance, start, terminal outcome, cancellation request/delivery and recovery. Consumption and release occur in the same transaction as the transition and signed evidence. A failed commit restores the slot. Every mandatory payload is limited to 64 KiB; reserved payload bytes are a conservative budget, not allocated RAM or total database size.

Protocol-2 ACK, result and output routes use their existing durable execution identity, fence and checksums. Successful retries return the persisted receipt without new HTTP intent/result records. Authentication and authorization denials remain audited. This does not change the auditing policy for other mutation routes. Heartbeat lease/contact updates and output byte/sequence counters are operational telemetry; execution state, identity, reason and result checksum changes still require mandatory evidence. A no-op order lock is not a business mutation.

Batch export accepts at most 128 records and 1 MiB per request. The collector validates continuity and replay identity, writes and syncs the journal, then acknowledges a contiguous prefix. The exporter advances only that prefix. Lost responses can resend records safely. Partial writes or sync failures stop the collector until its journal is recovered; never discard the journal to hide a gap. Multiple exporters may resend the same prefix; each collector journal still requires a single owning process.

Incremental scheduling

The scheduler keeps a deduplicated candidate queue, condition consumer indexes and due-time heap. Database triggers coalesce changes entering or leaving WAITING/RUNNING in scheduler_changes; terminal history inserts do not occupy the notification queue. Version-checked consumption avoids deleting a newer notification. Each tick reads at most 256 notifications and a 256-row reconciliation page. Candidate evaluation yields after 100 ms and requeues unfinished work. Claims, fencing, leadership and frozen instance snapshots retain their existing transaction rules.

A full keyset pass recovers lost notifications; the next pass starts 30 seconds after completion. Agent/resource blockers retry after two seconds, running candidates after one minute. At a two-second tick, scanning 28,800 rows takes roughly 113 ticks before evaluation delays; the reconciliation interval is not a 30-second recovery guarantee. The validated-plan cache holds at most 1,024 entries. Condition-pool reads and existing running/resource maintenance remain; incremental mode does not eliminate every database scan.

Reconciliation reads retained rows in the current business date, including terminal history. At 256 rows per tick and a two-second tick, nominal pass times are 226 seconds for 28,800 rows, 782 seconds for 100,000, 1,954 seconds for 250,000, and 7,814 seconds for 1,000,000. These are arithmetic estimates, excluding delays and the 30-second pause between passes, not measured recovery guarantees. Durable notifications normally provide the faster path; lost-event recovery and restart must still be evaluated at each density. Ordering within a selected batch does not by itself prove global FIFO across pages. Keep these gates distinct from ordinary dispatch throughput when deciding whether a larger tier is qualified.

Startup failures after an upgrade

A running systemd process does not imply that the API is listening. If nginx reports connect() failed (111: Connection refused) for the configured upstream, check the backend listener and startup journal before changing login credentials. Startup verifies the complete signed audit ledger before serving requests. A large retained history can take several minutes, especially on a VPS with high CPU steal. Logs identify the start and completion of that verification; it must not be bypassed or repaired by deleting ledger entries.

Definition snapshots have a separate -definitions-build-timeout (default 5m). The previous fixed 30-second budget could fail after the expensive audit verification and cause systemd to repeat the entire startup. Increase the budget for a large workspace on a constrained host, for example -definitions-build-timeout=10m. Timeout, cancellation, inconsistent files and parse failures still prevent publication of an incomplete snapshot.

-definitions-reconcile-interval (default 15s) controls the pause after a completed periodic scan. A slower host can use 60s; external file changes may then take longer to appear. Application and coordinated Git mutations still invalidate the cache immediately. Slow scans no longer accumulate periodic ticks that immediately start another scan.

The optional loopback profiler starts before database and audit initialization, after static configuration validation. It can therefore diagnose startup CPU as well as steady-state execution. -check-config still opens no listeners. Compare server, collector and agent versions individually: updating the server alone does not update an independently installed agent.

Profiling is disabled by default. Use -profiling-addr 127.0.0.1:6060 or REGENTE_PROFILING_ADDR=127.0.0.1:6060; only numeric loopback addresses are accepted. The listener is separate from the public router. It has no HTTP authentication: access it through a protected host or SSH tunnel. Profiles can contain private paths and workload data; store them with restricted permissions.

CPU and trace durations are bounded to 1–60 seconds. Heap, allocations, goroutine, thread, block and mutex profiles are available; block/mutex sampling is not enabled automatically. Capture the same workload, hardware, binary SHA, flags, database density and reader rate before and after. Report process CPU separately from host steal time. A successful health request is not proof of execution progress.

/metrics includes regente_perf_stage_seconds histograms for definition digest/read/normalization/build, workspace view, audit persistence/export, and scheduler selection/evaluation. Fixed-label counters report cache hits/builds/failures, receipt replays, rejected admission, exported records, evaluated candidates and reconciliation pages. Additional gauges expose definition readiness, reserved records/payload bytes, incremental pending/tracked/plans and reconciliation age. Existing audit lag/backlog, execution latency and completed-tick metrics remain necessary. /readyz distinguishes attempted ticks from completed progress; scheduler staleness is informational for followers and externally triggered scheduling.

Local qualification

# Contract/regression suite; PostgreSQL cases require REGENTE_TEST_PG_DSN.
go test ./server/... ./agent/...
REGENTE_TEST_INCREMENTAL=1 go test ./server/internal/scheduler -count=1
# Linux/amd64, real PostgreSQL, agents and independent TLS collector:
python3 scripts/capacity.py --perf-compare
python3 scripts/capacity.py --perf-day

--perf-compare runs the same 28,800-definition workload with full scheduling/single-record export and then incremental scheduling/batch export. Both use schema 33, the definition cache and audit reservations; this is not an old-binary comparison. It records process profiles, collector RSS and container CPU/memory limits. It does not qualify a daily capacity.

The last command requests a real 24-hour run with business-date rollover before higher tiers (28,800, 100,000, 250,000 and 1,000,000 orders/day offered rates), then a recovery soak at the last supported rate. CPU/heap profiles are saved with owner-only permissions; samples retain host CPU jiffies (including steal) separately from process CPU. A failed daily gate blocks higher tiers. Retained terminal rows are fixtures; actual admitted attempts, verified effects and distinct executed graph definitions are counted separately. The daily gate requires all 28,800 graph definitions to execute. The synthetic graph contains 900 components with fan-out and short chains using permanent conditions, mixed COMMAND/HTTP jobs, output and retries. It is not a qualification of the operator's production topology. --perf without --perf-day is a short engineering comparison and cannot close the daily gate.

Require bounded queues, correct receipts/effects, acceptable CPU/RSS and dispatch/reader latency, fault recovery and the complete versioned verification gates before deployment. Preserve failures and skipped gates in the report. Short quiescent SQLite benchmarks do not establish PostgreSQL throughput, VPS CPU reduction, a daily SLO, or one-million-per-day capacity.

The synthetic graph uses schedule.keepActive=2, recorded in the report, so admitted waiting jobs can cross the business-date rollover. The product default of zero intentionally expires never-started waiting jobs at the first rollover; this fixture setting does not change that behavior.

Capacity profiles use integration/compose.capacity.yaml, with PostgreSQL data on a dedicated Docker volume owned by the disposable run. The runner removes that volume during cleanup. This differs from the short integration suite's RAM-backed tmpfs; do not combine their results as one storage configuration. The report verifies the actual data mount and records PostgreSQL's Docker CPU/memory limits separately. A zero Docker limit means no explicit container limit; the runner's cgroup budget does not include this separate database.

The capacity runner accepts explicit --fast-slots and --slow-slots (defaults 4 and 1, respectively). Every result records both. Use identical concurrency for both halves of a comparison; changing slots defines a new capacity envelope and must not overwrite a failed report. Long-job capacity includes receipt/polling latency in addition to the three-second external command. CPU profiles cover the first 30 seconds, including any admission stop inside that window.

Read evidence while the laboratory runs

python3 scripts/perf_report.py .integration/RUN_ID/evidence > perf-summary.json

The analyzer is read-only and uses one sample at a time. It accepts a live or copied evidence directory, stops at the file size observed when opening it, and reports an incomplete trailing line instead of consuming a partial write. Invalid complete records, nonfinite values and out-of-order timestamps fail analysis. It reports counter resets, missing observations, sample gaps, CPU per elapsed interval, peak server/collector RSS, queue ages and counters. Reconciliation age -1 is counted as unavailable, not a fresh reconciliation. Host steal is separate from process CPU, and guest time is not counted twice.

No final capacity.json means there is no final report; it does not prove the process is still alive. The analyzer retains the runner's reported verdict and limitations but never grants qualification. Samples include the injected outage, so their maxima must not be substituted for the runner's fault-window-aware acceptance decision. Preserve the original files, binary SHA and final report.

A --perf-day run needs the host awake with Docker running for at least 24 hours, plus higher tiers, recovery and verification. Screen lock is fine; suspension, shutdown or stopping Docker interrupts the experiment. Record an interrupted run as incomplete and restart the full measurement window when rerunning it.

Diagnose a failed daily gate before repeating it

Keep the failed capacity.json, sample journal, attempt records and profiles. A short regression can exercise the same 28,800-definition graph, a real business rollover and paused-agent recovery without claiming a full-day qualification:

python3 scripts/capacity.py --perf-check --tier-seconds 600 --fast-slots 128 --slow-slots 64

This uses a disposable PostgreSQL volume with durable commits enabled. Its seed sets rollover five minutes ahead; normal daily runs keep their twelve-hour offset. A passing short check does not substitute for --perf-day or authorize higher tiers. Use the same host resource configuration and finish other verification work before beginning the isolated daily measurement.

Sample journals now include Linux pressure and cgroup I/O/CPU data. Bounded latency alerts capture PostgreSQL transaction wait types/blocking PIDs, process I/O counters and server goroutine stacks. These files omit SQL text, command arguments and credentials. Capture errors remain explicit. The report analyzer correlates the peak host I/O-wait interval with outbox and scheduler ages; host I/O wait includes unrelated workloads and does not identify the responsible disk or prove an application bottleneck. Diagnostic capture does not relax budgets.

The agent drains at most 32 deliveries per tick and acknowledges a newly persisted entry immediately, retaining concurrency and pending-journal limits. Acceptance still follows journal persistence, and effects still require durable start authorization. A partial SQLite index excludes acknowledged tombstones from the pending scan while retaining them for duplicate detection across restarts.

Isolate a failed scale tier

For engineering diagnosis after a failed scale run, use:

python3 scripts/capacity.py --perf-tier 250000 --tier-seconds 300 --fast-slots 128 --slow-slots 64

This repeats the selected tier on a disposable PostgreSQL volume with the same budgets, workload peaks and receipt/effect checks. It does not grant daily or progressive-scale qualification and does not run the recovery soak. Preserve the failed report and repeat the required qualification after accepting a correction. PostgreSQL lock acquisition uses row locks without no-op row updates; SQLite keeps its write-lock mechanism. Audit/queue/order lock ordering and synchronous commits remain mandatory.

Repeated identical agent presence, capacity heartbeats and credential last-use telemetry are coalesced over approximately one second. Capacity or metadata changes are persisted immediately. Authentication, revocation and certificate checks still run on each request; no authorization decision is cached.

Keep delivery responsive while draining results

The durable agent alternates existing journal entries with new deliveries, up to 32 deliveries per tick. An empty poll still allows the existing journal to drain. Capacity checks count pending entries through the partial index without loading their definitions or output. Acceptance, start authorization and output receipts retain their durability and replay requirements.

Runtime monitoring uses a read-only candidate filter before acquiring execution write locks: due runtime actions, expired SLA thresholds, or a matching slow rule with completed history. Rules and history are read again on subsequent ticks; no negative result is cached across ticks. Candidate effects are still validated and committed under the existing transactional leadership and execution locks. This reduces empty transactions, but does not itself establish a capacity rating.
