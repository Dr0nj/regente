# Install Regente on an existing Kubernetes cluster

> **EM DESENVOLVIMENTO E TESTES / IN DEVELOPMENT AND TESTING.**
> This installer and its container images are experimental, not production-qualified.
> Passing local kind checks is not acceptance on a public VPS. Kubernetes work is
> paused after this increment while testing prioritizes the native Linux server
> on a VPS. Use this guide for evaluation with recoverable test data.

This is the application installer. It does **not** install Kubernetes. The older
`lab.py` recipes qualify individual architectures; they are not this installer.

Topology: one PostgreSQL StatefulSet, one Regente server (including the web UI),
and one independent worker StatefulSet. Commands/scripts run **inside the worker
pod**, not on the node or an external Linux host. The worker has no Kubernetes
service-account token or Docker socket. Its journal is on its own PVC.

The initial distribution targets Linux/amd64, K3s with Traefik, an existing
cert-manager ClusterIssuer, and a dynamic StorageClass. The same core installer
is exercised on kind in the release workflow. Public DNS/ACME and VPS operation
remain environment-specific checks, not claims of HA or disaster recovery.

## Before starting

Have a working kube context, storage provisioner, Traefik and cert-manager, with
a Ready public ACME ClusterIssuer. Point your domain at the ingress IP. Keep the
cluster version supported by your infrastructure provider. The operator needs
namespace/workload/Secret permissions and permission to inspect nodes, CRDs and
StorageClasses. Python 3.11+ and kubectl must be available on that machine.

Use the **same release** for server, worker and installer. Releases include:

- `regente-kubernetes-installer.tar.gz` — the executable installer and this guide;
- `kubernetes-images.json` — immutable GHCR image references, version, source SHA;
- `kubernetes-qualification.json` — the local functional qualification evidence;
- the signed release manifest, which inventories these assets as well as native binaries.

Verify the downloaded assets with the release signature/checksums before use.
For a private GHCR package, add `registryConfigFile` to install.json with the path
to a protected Docker config JSON containing inline registry `auths` (mode 0600).
The installer creates the namespace-scoped imagePullSecret. It does not turn a
package public or silently use your personal registry login/credential helper.
An `ImagePullBackOff` is an incomplete installation, not a successful bootstrap.

## One supported flow

Extract the installer bundle into a working directory. Create a protected state
directory **outside your Git checkout**. This directory holds recovery credentials
and must survive subsequent installer runs.

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
install -d -m 700 "$HOME/.local/state/regente-production"
cp install.example.json install.json
```

Edit `install.json`: select the exact context, a **new** namespace, environment,
domain, publicIssuer, storageClass, workspace HTTPS URL/branch, and a stable
agentId. Copy serverImage and agentImage from `kubernetes-images.json`; use
`@sha256:...`, never `latest`. Do not put secrets in this file or Git URLs.

```sh
.venv/bin/python install.py --config install.json \
  --state-dir "$HOME/.local/state/regente-production"
```

The first run prompts privately for the administrator password and Git token.
Empty Git token is allowed for a public read-only workspace. Use the same command
and state directory to resume a failed installation or reconcile the deployment.
Do not run two installers against the same installation concurrently.

The installer refuses to adopt an existing namespace without its matching state.
It also refuses to change the cluster/namespace/environment/agentId/workspace
identity in-place. Image references can change together for a planned upgrade.

## What the code does and verifies

1. Checks cluster readiness, storage and required ingress/certificate resources.
2. Creates persistent data volumes and internal TLS identities. PostgreSQL rejects
   plaintext network connections; Regente uses `sslmode=verify-full` with its CA.
3. Starts the server after PostgreSQL is ready. Root filesystems stay read-only;
   `/data` and `/tmp` are writable mounts. Audit keys are generated by Regente's
   own Ed25519 implementation on the data volume, not by an ad hoc shell encoder.
4. Logs in and registers the worker using one agentId/environment/capability set,
   matching certificate fingerprint and token. An init container validates the
   persistent journal before the polling process starts.
5. Runs one isolated, schedule-disabled smoke job and checks `OK`, output, a
   persisted instance receipt and exactly one line of effect on the worker PVC.
   It checks a live PostgreSQL TLS connection. Retrying never reorders this job.
6. Enables the real Git workspace in a **different** directory, waits for a commit,
   opens a Design folder session, reads it and discards that clean test session.
   It does not publish a test change to your Git repository.
7. Removes both bootstrap environment references, verifies rollout, removes the
   temporary Secret keys and verifies login again.
8. Configures public TLS and verified Traefik-to-server TLS; validates the public
   HTTPS readiness endpoint with normal certificate verification.

Successful output includes protected `install-report.json` and `install-report.md`,
with version/image references, source commit, fingerprint, credential expiry,
smoke instance and the completed checks. No passwords, tokens or private keys
belong in the report. `local-verified` deliberately excludes public HTTPS.

The Git workspace is live after step 6: enabled schedules can create orders and
run jobs whose environment/capabilities match the worker. Review your definitions
before connecting a production workspace. An imported job waiting for a condition,
window, confirmation or matching executor is not automatically a failed job.

## Storage contract

| Path / volume | Purpose |
|---|---|
| `/data/workspace` / server-data | Synchronized Git definitions |
| `/data/sessions` / server-data | Design clone cache; durable drafts also live in DB |
| `/data/audit.key` and `.pub` / server-data | Audit signing identity; preserve with DB |
| `/data/bootstrap-workspace` / server-data | Isolated installer smoke definitions |
| `/state/agent.db` / agent-journal | Worker identity and durable execution receipts |
| PostgreSQL data / postgres-data | Users, schedules, orders, drafts and audit ledger |

`REGENTE_SESSIONS_DIR` / `-sessions-dir` overrides the session cache location.
When omitted, the server uses `sessions` beside the configured workspace. It
tests write access at startup when GitOps is enabled. Linux/systemd and Kubernetes
therefore use the same explicit storage contract. The container's working directory
is `/data`, which also keeps relative archive paths off the read-only image.

## Existing manually installed VPS

Do not point this fresh-install workflow at the existing namespace or erase PVCs.
Preserve PostgreSQL, audit key, worker journal/identity, manifests and credentials;
verify a restore in isolation before migrating. Existing Docker executors and the
new worker pod are different execution locations. Host scripts/files are not
magically present in the pod.

For an older image reporting `mkdir sessions: read-only file system`, the compatible
immediate repair is to set the **server container's workingDir to its existing
writable `/data` mount**, then verify rollout and opening a folder. Keep
`readOnlyRootFilesystem: true`. On the new image also set
`REGENTE_SESSIONS_DIR=/data/sessions`. Confirm mount and container names against
the actual Deployment before patching; never replace the entire Deployment with a
lab manifest. A successful login or `/readyz` did not validate Design storage.

## Credentials, upgrade and recovery

Worker tokens expire after 90 days. Before expiry, rotate token and client
certificate together using the same identity and journal:

```sh
.venv/bin/python install.py --config install.json \
  --state-dir "$HOME/.local/state/regente-production" --rotate-agent-credential
```

The old credential has a five-minute grace period. The worker is rolled out with
the new protected credential; its journal is preserved. The command reports the
next expiry. Rotation requires an active token; expired/revoked credentials or a
lost rotation receipt require explicit recovery rather than silently creating
duplicate identities. If the administrator password was changed in the UI, update
the protected installer state before reconciliation; do not print it in a ticket.

Internal server/database certificates currently have a one-year lifetime and the
CA ten years. Automatic internal-PKI renewal is **not yet implemented**; their
expiry is reported. Plan renewal and PostgreSQL reload before that date. Public
ACME renewal is managed by cert-manager. Do not confuse the two lifecycles.

Before upgrading, stop admitting new work, account for running/UNCERTAIN attempts,
back up PostgreSQL plus server-data, agent-journal and protected installer state,
and test restoration on an isolated installation. Change both image digests to
the same qualified release and rerun. A binary rollback is only safe with schema
compatibility and a reconciled journal; restoring the DB alone can repeat effects.
Off-host backups, restore drills, storage failover, capacity and HA are deployment
responsibilities beyond this initial single-replica installer.

## Specific failure diagnostics

| Symptom | Check / recovery |
|---|---|
| Design mkdir/read-only | sessions directory, server workingDir, volume and UID65532 ownership |
| Agent HTTP403 | exact agentId, environment, capabilities, token binding and certificate fingerprint |
| Journal incompatible | stop and preserve the journal; recover the original identity; never delete it to make polling green |
| PostgreSQL TLS | DSN verify-full, CA, `postgres` hostname SAN and the live pg_stat_ssl connection |
| Git not synchronized | source URL, branch, token permissions and `/api/git/status`; do not call setup complete |
| Set OK does not release a successor | read both frozen order snapshots, condition name + order date, `/api/conditions` and `/api/instances/{id}/explain` |
| Bootstrap Secret missing | remove both bootstrap refs in a verified rollout before deleting credential keys |
| Expired credential | recover/rotate explicitly; keep agentId and journal paired |

Set OK applies the **ordered snapshot's** output conditions. Editing Design after
an order was created does not rewrite it. In durable mode the server emits
`condition.changed` after the Set OK transaction commits, so Monitoring refreshes
the same condition pool used by the scheduler. A condition can be consumed by a
successor's OUT−; a missing visual line alone does not prove it was never emitted.

For a failed install, inspect pods, events and rollout in the configured namespace.
Keep the protected state and reports. Fix the reported cause and rerun; do not
restart from a new identity or destroy the only copy of the journal.
